# Codex-Ready Writing Rules Standard

## 1. Purpose

This standard defines how Web App Prompt Kit documents should be written so that Codex can execute them safely, narrowly, and with minimal inference.

Codex-ready writing means every generated document should make its owned facts, rules, boundaries, references, and validation expectations clear enough for task-scoped implementation.

This standard applies to review records, reference catalogs, execution documents, and prompt outputs generated by this kit.

## 2. Scope

This standard governs writing style and structural clarity.

It applies to:

- `docs/review/*`
- `docs/reference/*`
- `docs/reference/ui/*`
- `docs/execution/*`
- prompt outputs that generate the files above

It does not define:

- product requirements
- domain rules
- architecture boundaries
- API contracts
- frontend or backend implementation details
- validation commands
- runtime task execution policy

Those belong to their owning documents.

## 3. Core Principle

Final documents should read as resolved instructions and stable references, not brainstorming notes.

A Codex-ready document should answer:

- what is true
- what is required
- what is forbidden
- what the current implementation pass includes
- what Codex may rely on without guessing
- what downstream document owns each type of detail

It should not leave Codex to decide:

- what the product should do
- which architecture should be chosen
- what API shape should exist
- what UI flow is required
- which validation command proves a task
- whether unresolved questions should be resolved during implementation

## 4. Rule Catalog

### RULE-001: Use Stable, Addressable IDs

Requirement:
- Use stable IDs for durable reference entries.

Applies To:
- review records
- reference catalogs
- execution documents

Required:
- Use the correct ID family for the owning document.
- Make Markdown IDs heading-addressable when possible.
- Use stable YAML keys for YAML references.

Recommended ID Families:

| ID Family | Owner |
|---|---|
| `DEC-*` | `docs/review/project-decisions.md` |
| `REQ-*` | `docs/reference/product-spec.md` |
| `ENT-*` | `docs/reference/domain-model.md` |
| `REL-*` | `docs/reference/domain-model.md` |
| `BR-*` | `docs/reference/domain-model.md` |
| `STATE-*` | `docs/reference/domain-model.md` |
| `ARCH-*` | `docs/reference/architecture.md` |
| `DB-*` | `docs/reference/data-api-contract.md` |
| `API-*` | `docs/reference/data-api-contract.md` |
| `ERR-*` | `docs/reference/data-api-contract.md` |
| `TYPE-*` | `docs/reference/data-api-contract.md` |
| `FE-*` | `docs/reference/frontend-design.md` |
| `BE-*` | `docs/reference/backend-design.md` |
| `ENV-*` | `docs/reference/dev-environment.md` |
| `FLOW-*` | `docs/execution/execution-validation.md` only |
| `TASK-*` | `docs/execution/execution-validation.md` |
| `VAL-*` | `docs/execution/execution-validation.md` |

Forbidden:
- Do not create IDs owned by another document.
- Do not use `OQ-*` outside review-stage question artifacts.
- Do not create `FLOW-*` in final reference catalogs.

Check:
- Every referenced ID exists in the owning document.

### RULE-002: Use Final Document Paths

Requirement:
- Use the three-folder target structure consistently.

Required:
- Use paths under:
  - `docs/review/`
  - `docs/reference/`
  - `docs/execution/`

Preferred Examples:

```text
docs/review/project-decisions.md#DEC-001
docs/reference/product-spec.md#REQ-001
docs/reference/data-api-contract.md#API-001
docs/reference/ui/UI_PAGE.yaml#page_proposal_app
docs/execution/execution-validation.md#TASK-001
```

Forbidden:
- Do not use legacy flat paths such as:
  - `AGENTS.md`
  - `docs/product-spec.md`
  - `docs/project-decisions.md`
  - `docs/execution-validation.md`
  - `docs/ui/UI_PAGE.yaml`

Check:
- Generated references use the required target paths.

### RULE-003: Keep Source-of-Truth Ownership Clear

Requirement:
- A document must not redefine content owned by another document.

Required:
- Reference the owner document when using another document's content.
- Summarize only enough to make the current entry understandable.

Forbidden Examples:
- `frontend-design.md` defining API response shapes.
- `backend-design.md` defining database schemas as source of truth.
- `architecture.md` defining Docker command catalogs.
- `execution-validation.md` redefining business rules.
- `AGENTS.md` defining new product requirements.

Check:
- Each definition appears in exactly one owning document.

### RULE-004: Write Final Documents as Resolved Content

Requirement:
- Final reference and execution documents must contain answers, not unresolved questions.

Required:
- Convert resolved uncertainty into durable rules, requirements, contracts, decisions, or tasks.
- Stop final generation if blocking uncertainty remains.

Forbidden Markers in Final Reference and Execution Docs:
- `Open Questions`
- `TBD`
- `to be decided`
- `unclear`
- `unknown`
- `ask user later`
- `decide later`
- `pending decision`
- `OQ-*`

Allowed Locations for `OQ-*`:
- `docs/review/open-questions-review.md`
- `docs/review/question-resolution.md`

Check:
- No unresolved markers appear in final reference or execution documents.

### RULE-005: Use Current Implementation Framing

Requirement:
- Frame documents around the current implementation pass.

Preferred Terms:
- current implementation pass
- current implementation scope
- requested capability
- scope boundary
- completion criteria
- validation criteria
- flow slice
- flow-level validation

Avoid:
- MVP
- future scope
- deferred feature
- roadmap
- later version
- full product evolution

Allowed Exception:
- Historical notes may mention older wording only when explaining a migration or standards change.

Check:
- Final documents do not imply unapproved roadmap planning.

### RULE-006: Write Flow-Aware Product and Execution Content

Requirement:
- When describing app behavior, write through flow concepts rather than only features, pages, APIs, or modules.

Required:
- Use the terminology from `standards/flow-concepts-and-composition.md`.
- Distinguish product-facing Core User Flows from execution-level `FLOW-*` entries.
- Represent Side Effect Flows when system effects are required for completion, observability, recovery, artifacts, or validation.

Do Not:
- Treat every page as a flow.
- Treat every API endpoint as a flow.
- Treat every Interaction Effect as a standalone Execution Flow.
- Generate execution `FLOW-*` entries in product, domain, API, frontend, or backend reference documents.

Check:
- Product flows, side effects, feedback, recovery, state transitions, and completion signals remain traceable into downstream documents.

### RULE-007: Make Scope Boundaries Explicit

Requirement:
- Important entries should state what is included and excluded.

Required:
- Use `Out of Scope`, `Forbidden`, `Boundary`, or equivalent sections when needed.
- Boundaries should prevent Codex from expanding implementation scope.

Good:

```text
Out of Scope:
- Authentication in the current implementation pass.
- Runtime plugin marketplace.
- Non-required export formats.
```

Weak:

```text
Add later.
Maybe support more things.
```

Check:
- Codex can tell what not to implement.

### RULE-008: Prefer Specific, Testable Language

Requirement:
- Avoid vague instructions that force Codex to improvise.

Avoid:
- handle errors properly
- make it user friendly
- support common files
- improve architecture
- add tests
- wire things up

Prefer:
- Return `ERR-002` for unsupported upload extensions.
- Disable the submit action while the create-run request is pending.
- Keep user input available after a recoverable API failure.
- Validate that artifact download rejects unsafe paths.

Check:
- A reviewer can understand what concrete behavior must exist.

### RULE-009: Use Tables for Traceability, Not Decoration

Requirement:
- Use tables when mapping relationships or proving coverage.

Good Table Uses:
- question-to-resolution mapping
- document ownership
- API fields
- data fields
- flow-to-reference mapping
- task dependencies
- task-to-validation mapping
- validation claims

Avoid:
- Tables that repeat prose without adding traceability.
- Overly wide tables that hide critical details.

Check:
- Each table makes a relationship clearer than prose alone.

### RULE-010: Keep Reference Entries Compact and Independently Readable

Requirement:
- Reference catalog entries should be small enough for task-scoped reading but complete enough to use safely.

A Strong Entry Includes:
- stable ID or key
- title
- purpose or meaning
- rules or constraints
- related IDs
- boundaries when useful

Avoid:
- long rationale
- implementation diary
- duplicated definitions
- unresolved questions
- task execution instructions
- validation commands outside environment or execution ownership

Check:
- Codex can read a referenced entry without reading the full document by default.

### RULE-011: Write Task-Scoped Source References

Requirement:
- Execution tasks must specify exactly what Codex should read.

Required:
- `TASK-*` entries should include precise `Read Before This Task` sources.

Good:

```text
docs/reference/data-api-contract.md#API-001
docs/reference/backend-design.md#BE-003
docs/reference/dev-environment.md#ENV-004
```

Avoid:
- all docs
- project documentation
- architecture
- product spec

Check:
- Codex does not need to infer which references to read.

### RULE-012: Write Executable Tasks

Requirement:
- `TASK-*` entries must be narrow, scoped, and validated.

A Task Should Include:
- task type
- priority
- dependencies
- goal
- read-before sources
- implementation scope
- expected code impact
- out-of-scope boundaries
- required validation
- completion rule

Forbidden:
- Large mixed tasks that implement all backend, all frontend, and all data at once.
- Tasks that require unresolved decisions.
- Tasks that have no validation or blocker path.

Check:
- Codex can complete the task without making design decisions.

### RULE-013: Write Meaningful Validation Claims

Requirement:
- Every validation entry should prove a specific claim.

Required:
- Validation entries should include purpose, command, claim proven, used by, and failure meaning.

Weak:

```text
Run tests.
Make sure it works.
```

Strong:

```text
Proves unsupported upload extensions return `ERR-002` and do not create a run workspace.
```

Check:
- Validation explains why the command matters.

### RULE-014: Preserve Flow-First Execution Without Hiding Foundation Work

Requirement:
- Execution writing must support flow-first implementation while making necessary foundation explicit.

Required:
- Foundation tasks must unlock named flows.
- Flow slice tasks must list prerequisites or dependencies.
- Broad layer-first work must be avoided.

Do Not:
- Start a flow slice before its minimum reusable foundation is identified.
- Create broad foundation tasks that implement full technical layers.
- Hide bootstrap, command policy, contract, or validation setup inside a flow task when it is reusable and required before the flow.

Check:
- Every flow slice can be executed without Codex inventing missing foundation.

### RULE-015: Keep Runtime Worklog Rules in AGENTS

Requirement:
- `docs/execution/codex-execution-report.md` is a runtime worklog managed by `docs/execution/AGENTS.md`.

Required:
- AGENTS must instruct Codex to create the worklog when missing.
- AGENTS must define what the worklog records.
- The worklog must not become a source-of-truth document.

Forbidden:
- Treating `codex-execution-report.md` as a normal ChatGPT-generated reference file.
- Defining new requirements, decisions, contracts, tasks, or validation criteria in the worklog.

Check:
- Runtime reporting policy appears in AGENTS, not a separate standard dependency.

## 5. Required Practices

Generated documents should:

- use stable IDs and final paths
- respect document ownership boundaries
- use current implementation framing
- make scope boundaries explicit
- preserve flow terminology consistently
- keep final reference documents free of unresolved questions
- keep execution tasks task-scoped and validation-driven
- keep runtime worklog behavior governed by AGENTS

## 6. Forbidden Practices

Generated documents must not:

- mix old and new target paths
- leave unresolved questions in final reference or execution docs
- use `OQ-*` outside review question artifacts
- redefine another document's source-of-truth content
- use vague implementation language where specific behavior is needed
- organize execution as all data, then all backend, then all frontend
- ask Codex to infer tasks from reference catalogs
- mark tasks complete without validation or recorded blocker

## 7. Prompt Integration

Prompts should not paste this entire standard into their output.

Prompts should:

- list this standard under `Required Standards` when writing quality, path, ownership, or execution-readiness matters
- apply only the rules relevant to the current output
- avoid duplicating the full standard text inside generated project documents

Recommended usage:

| Prompt Type | Use This Standard? | Purpose |
|---|---:|---|
| discovery/review prompts | yes | keep wording current-scope and flow-aware |
| reference prompts | yes | enforce ownership, IDs, and resolved content |
| UI prompts | yes | avoid unresolved questions and ownership drift |
| execution prompts | yes | enforce task-scoped, validation-driven writing |
| AGENTS prompt | yes | enforce runtime policy clarity |
| cross-document review prompt | yes | inspect compliance |

## 8. Review Checklist

A document or prompt output is compliant when:

- paths use the required `docs/review`, `docs/reference`, and `docs/execution` structure
- IDs belong to the correct owner documents
- final documents contain resolved content only
- Open Questions remain only in review-stage question artifacts
- flow terminology is used consistently
- scope boundaries are explicit
- reference entries are compact and addressable
- execution tasks are narrow and validated
- validation claims are specific
- AGENTS governs runtime worklog creation and updates
- Codex is not asked to guess product, architecture, API, UI, or validation decisions
