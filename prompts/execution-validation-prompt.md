# Execution Validation Prompt

## Purpose

Use this prompt to generate the Codex execution spine for the current implementation.

The generated document is the primary task and validation source for Codex. It converts the review-stage flow composition, non-UI reference catalogs, and UI reference files into a flow-first implementation plan with executable `FLOW-*`, `TASK-*`, and `VAL-*` entries.

This prompt must produce a flow-first execution document, not a layer-first implementation plan.

## Target Output

Generate exactly one document:

```text
docs/execution/execution-validation.md
```

## Document Role

`docs/execution/execution-validation.md` is an execution document.

It owns:

```text
final executable FLOW-* entries when used
TASK-* entries
VAL-* entries
minimal foundation tasks
flow slice task catalog
cross-flow hardening task catalog
task-scoped source references
UI task-scoped source references
flow-level validation
UI-level validation expectations
task-to-validation mapping
release validation
execution readiness
```

It must not own:

```text
product requirements
domain source definitions
architecture source rules
API source contracts
frontend source responsibilities
backend source responsibilities
environment source policies
UI_PAGE source structure
UI_TOKENS source token definitions
UI_VISUAL_SPEC source presentation rules
Open Questions
Codex runtime worklog format source of truth
```

The runtime worklog file:

```text
docs/execution/codex-execution-report.md
```

is not generated by this prompt. It is created and maintained by Codex according to `docs/execution/AGENTS.md`.

## Standard Application Rules

Standards constrain how this prompt generates its target document. Standards do not create additional output targets.

Rules:
1. Read only the standards listed in this prompt.
2. Do not load all standards by default.
3. The current prompt defines the target output and required output structure.
4. Standards define reusable terminology, ownership boundaries, UI consumption rules, quality rules, and review constraints.
5. Do not copy large sections from standards into the generated document.
6. Do not generate documents requested by a standard unless this prompt explicitly targets them.
7. If required context remains unresolved under the standards, output a blocked-generation report instead of inventing missing decisions.

## Priority Rule

When generating the target document, use this priority order:

1. User-confirmed answers and corrections.
2. This prompt's target output and required output structure.
3. Required standards listed in this prompt.
4. `docs/review/flow-composition-review.md`.
5. Final reference catalogs and UI reference files.
6. Prior review documents and project discussion.

If a conflict involves unresolved blockers, Open Questions leakage, unsafe scope invention, missing required decisions, reference ownership redefinition, UI ownership redefinition, missing foundation readiness, missing UI surface readiness, or unverifiable tasks, output a blocked-generation report instead of generating a normal execution document.

## Core Execution Policy

The generated document must use Flow-first as its primary execution structure.

Flow-first means:

```text
minimal foundation tasks
→ executable flow slices
→ cross-flow hardening
→ release validation
```

It does not mean foundation-free.

It does not mean layer-first.

Forbidden execution structures:

```text
all data layer first
all backend second
all frontend third
all UI system fourth
wire everything together last
P0-P10 as the top-level execution structure
generic phase checklist as the task plan
```

Engineering completeness must be considered while composing tasks, but it must be absorbed into foundation tasks, flow slice tasks, hardening tasks, and release validation.

## UI Execution Policy

For UI-related tasks, Codex must read the `codex_consumption` section of each referenced UI YAML before modifying UI code.

UI task-scoped sources may include:

```text
docs/reference/ui/UI_PAGE.yaml
docs/reference/ui/UI_TOKENS.yaml
docs/reference/ui/UI_VISUAL_SPEC.yaml
docs/reference/frontend-design.md
docs/reference/data-api-contract.md when actions call APIs
```

UI references mean:

```text
UI_PAGE.yaml = flow-facing semantic UI surface
UI_TOKENS.yaml = technology-agnostic design token intent
UI_VISUAL_SPEC.yaml = visual and interaction presentation rules
```

UI references do not define:

```text
concrete styling stack
CSS variable mappings
Tailwind classes
shadcn/ui requirements
React component file paths
className strings
API request/response shapes
backend behavior
```

Codex should implement UI using:

```text
existing project stack
existing code conventions
task-scoped sources
frontend-design.md
execution-validation.md
```

while preserving UI surface, action semantics, state feedback, recovery behavior, artifact visibility, completion signal visibility, accessibility intent, and technology-agnostic token intent.

## Foundation Planning Rules

Before generating `TASK-*`, use the Flow Readiness and Foundation Planning logic from `flow-composition-review.md`.

Foundation tasks must be:

```text
minimal
reusable
required before one or more flow slices
explicitly tied to the flow(s) they unlock
```

Every foundation task must include:

```text
Unlocks:
- FLOW-...
```

A foundation task must not implement:

```text
all backend
all frontend
all data layer
all UI system
all styling system
all API routes
all validation
```

If a foundation element is only needed by one flow and is safe to implement inside that flow slice, keep it inside that flow slice task.

If a later flow introduces a new reusable prerequisite, create a narrow enabling task immediately before that flow or include it inside the flow slice when local.

## Flow Slice Rules

Each executable `FLOW-*` should represent a behavior that can be implemented and validated.

A `FLOW-*` may derive from:

```text
Core User Flow
Side Effect Flow
Supporting Interaction Flow
Feedback Flow
Recovery Flow
Status Feedback Flow
Artifact Flow
Blocked Flow
System Support Flow
```

Each `FLOW-*` must include:

```text
goal
flow type
trigger / start condition
required foundation
UI surface summary when user-visible
completion signal
task coverage summary
validation summary
```

A flow slice task must include all layer work necessary for that behavior, such as frontend, UI surface, API, backend, data/storage, artifact handling, feedback, recovery, and validation responsibilities, but only to the extent required by that flow.

Do not split a flow into layer-only tasks unless the split is necessary and each task still has a clear flow relationship.

## Reference and UI Use Rules

Execution tasks may reference source IDs and UI references from reference documents, but must not redefine them.

Allowed:

```text
Read before this task:
- docs/reference/data-api-contract.md#API-001
- docs/reference/frontend-design.md#FE-003
- docs/reference/ui/UI_PAGE.yaml#page_generator
- docs/reference/ui/UI_VISUAL_SPEC.yaml#states.failed
```

Forbidden:

```text
TASK-010 defines the create-run API request fields.
TASK-011 defines new UI_PAGE actions.
TASK-012 defines Tailwind classes for the primary button.
```

Task entries should use task-scoped source references.

Do not instruct Codex to read all reference documents by default.

Do not instruct Codex to infer tasks from reference catalogs or UI YAML files.

## Validation Rules

Every `TASK-*` must have required validation.

Every `VAL-*` must be claim-proven.

A validation entry must specify:

```text
purpose
command or evidence type
claim proven
used by
failure meaning
```

Validation may be:

```text
unit
integration
contract
frontend interaction
UI state evidence
API-level
backend service-level
flow-level
manual smoke
release-level
```

Do not write vague validation such as:

```text
run tests
check everything
verify manually
```

unless the command or evidence is explicitly stated and the claim is clear.

## UI Validation Rules

For UI-related tasks, validation should prove the relevant UI claim.

Possible UI validation claims:

```text
the documented action affordance exists
the action calls or triggers the documented behavior
the documented pending/running/submitting state is visible
failed or blocked state includes text-visible feedback
validation_failed state preserves correction affordance when required
recovery action is visible and actionable when defined
artifact surface appears when artifact is available
completion signal is visible to the user
critical state does not rely on color alone
keyboard/focus/accessibility expectations are satisfied where relevant
```

UI validation may be:

```text
frontend interaction test
component test
E2E test
manual smoke evidence
screenshot evidence when appropriate
accessibility check evidence
```

Do not require a specific UI testing stack unless `dev-environment.md` provides one.


Do not invent tool-specific commands that are not supported by `dev-environment.md`.

Do not invent UI testing-stack commands that are not supported by `dev-environment.md`.

## Completion Rule Requirements

Each task completion rule must state:

```text
required implementation done
required validation passes
runtime worklog updated according to AGENTS.md
or blocker recorded with evidence
```

UI-related task completion rules must also state, when relevant:

```text
referenced UI YAML codex_consumption was read
documented UI surface/action/state/feedback/recovery/artifact/completion behavior is preserved
```

Do not mark a task complete only because code was edited.

## Flow Readiness Checks

Before finalizing, verify:

- Every `FLOW-*` has a completion signal.
- Every user-visible `FLOW-*` has a UI surface summary.
- Every `FLOW-*` has required foundation listed.
- Every foundation task unlocks at least one flow.
- No flow slice starts before required foundation exists.
- No foundation task implements a full technical layer.
- No foundation task implements the entire UI or styling system.
- Side Effect Flows that affect completion, artifacts, state, recovery, UI feedback, or validation are represented or explicitly absorbed.
- Flow slices are not merely frontend-only or backend-only unless justified.
- Cross-flow hardening runs after relevant flows exist.

## Blocked Generation Rules

Output a blocked-generation report instead of a normal execution document if:

- `flow-composition-review.md` is missing and flow composition cannot be safely inferred
- unresolved Open Questions affect execution
- required reference docs are missing or contradictory
- required UI files are missing or contradictory for user-visible flows
- referenced UI YAML lacks required `codex_consumption`
- required foundation readiness cannot be determined
- a required flow cannot be validated
- a required UI claim cannot be validated by any known command or evidence type
- environment command patterns are missing for required executable validation
- API/frontend/backend/UI boundaries are too unclear for task planning
- task generation would require inventing product, architecture, API, FE, BE, ENV, or UI source content
- task generation would require assuming a concrete styling stack that is not established by the project

Blocked-generation report structure:

```markdown
# Execution Validation Generation Blocked

## Blocking Issues

| Issue | Decision Needed | Affected Flow / Task Area | Affected Source Docs |
|---|---|---|---|

## Partial Safe Execution Structure

## Required User Decisions
```

## Final Checks

Before finalizing, verify:

- The document is flow-first.
- The document does not use P0-P10 as the top-level structure.
- No unresolved Open Questions remain.
- No reference-owned content is redefined.
- No UI-owned content is redefined.
- No API payloads, DB schemas, product requirements, frontend responsibilities, backend responsibilities, UI_PAGE structures, UI_TOKENS tokens, or UI_VISUAL_SPEC presentation rules are newly invented.
- UI-related tasks reference UI YAML files task-by-task.
- UI-related tasks require reading `codex_consumption`.
- No concrete styling stack is assumed unless established by the project.
- All `TASK-*` entries have required validation.
- All `VAL-*` entries prove a concrete claim.
- UI-level validation exists for user-visible flow behavior.
- Codex is not asked to infer tasks from reference catalogs or UI YAML files.
- Codex execution report is treated as a runtime worklog managed by `AGENTS.md`.
